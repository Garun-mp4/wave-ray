# План полной переработки frontend RuView

**Статус:** основная sensing UI переработка реализована; границы проверки указаны в разделе 12

**Дата проверки:** 2026-10-10

**Проверенная версия:** `codex/backend-completion`, commit `821b6db`

**Основная цель:** сделать из набора разрозненных демонстрационных страниц понятную панель управления и наблюдения, которая показывает только то, что подтверждается текущим источником данных и backend.

## 1. Результат текущей проверки backend

Проверки выполнены в активной рабочей ветке `codex/backend-completion`. Локальный Go SDK и Go-зависимости на Windows не устанавливались: команды выполнялись в контейнерах.

| Проверка | Результат |
|---|---|
| Go-пакеты: `go test -mod=readonly ./...` | Прошли |
| Race detector: `go test -race -mod=readonly ./...` | Прошёл |
| `go vet -mod=readonly ./...` | Прошёл |
| `go mod verify` | Прошёл |
| Сборка `go build -trimpath` | Прошла |
| Основной Compose и профиль `legacy-python` | Конфигурация прошла проверку |
| Go production image и запуск с `CSI_SOURCE=simulate` | Образ собрался, контейнер стал healthy; health и UI вернули 200, API без токена — 401, с токеном — 200 |
| Режим `CSI_SOURCE=esp32` без физического узла | Контейнер healthy, источник честно сообщил `esp32:offline`, UDP-метрики доступны, новых кадров нет |
| Frontend Node-тесты (`ui/sw.test.mjs`, тесты сервисов и компонентов) | 46 тестов прошли |

В первом запуске всего backend-набора один тест RuField WebSocket завершился по таймауту во время параллельной проверки Compose. Изолированный тест прошёл 10 последовательных раз; затем полный набор и полный прогон с race detector прошли. Устойчиво воспроизвести дефект не удалось. При реализации надо оставить этот integration-сценарий под наблюдением CI, а не считать его доказательством безошибочной работы WebSocket.

**Вывод:** Go backend можно собрать и запустить в проверенных локальных режимах, а базовые API, авторизация и статическая раздача UI работают. Называть backend полностью функционально завершённым или подтверждённым на реальном sensing нельзя. По `backend/MIGRATION_STATUS.md` ещё не подтверждены физическим оборудованием CSI-приём, валидированная многолюдная метрическая локализация и pose, калиброванный field scorer и vitals; часть pose/model-training API явно отвечает `501`; полная совместимость всех Rust REST/WebSocket контрактов тоже не доказана. В интерфейсе эти возможности должны оставаться недоступными, экспериментальными или без данных, пока не появятся соответствующие измерения и валидация.

## 2. Что видно в существующем frontend

Основной frontend sensing-приложения сейчас — статическое приложение на HTML, CSS и нативных ES-модулях; у каталога `ui/` нет собственного `package.json`, обязательного frontend build step или SPA-фреймворка. Go image копирует `ui/` и раздаёт его напрямую. В репозитории также есть `dashboard/`, но его `package.json` и ADR-092 определяют его как отдельный Vite/TypeScript/Lit интерфейс симулятора nvsim; он подключается к `nvsim-server` и не является экраном Go sensing backend. В `ui/mobile/` и desktop crate есть другие самостоятельные интерфейсные поверхности. Их нельзя автоматически объединять или переписывать в рамках редизайна sensing UI. В основном `ui/` есть полезные API/stream-сервисы и модульные компоненты, но поверх них сложился неоднородный интерфейс:

- `ui/index.html` одновременно содержит рабочую панель, обзорные/маркетинговые блоки, сведения об архитектуре и производительности, учебную демонстрацию, настройки оборудования и обучение. В основной навигации восемь вкладок, а `Pose Fusion` и `Observatory` вынесены в отдельные HTML-страницы.
- `ui/observatory.html`, `ui/pose-fusion.html` и `ui/viz.html` выглядят как самостоятельные приложения с отдельными HUD, навигацией, состояниями и визуальными правилами. Их реальные источники данных и демонстрационные сценарии надо инвентаризировать до объединения.
- `ui/app.js` отвечает за bootstrapping, сервисы, компоненты и многочисленные глобальные enhancements; `ui/style.css` содержит около 4,200 строк. Это не доказывает, что каждую часть надо переписать, но показывает, что до редизайна нужны инвентаризация зависимостей, границ и дублирования.
- В интерфейсе есть `mock-server`, автоматическое определение mock/backend, тесты API/stream и статические состояния. Надо проверить, когда именно UI сам включает mock, и заменить любое неочевидное переключение явным выбором режима, чтобы демонстрационные данные не выглядели live-измерениями.
- Найдены устаревшие и неподтверждённые формулировки: “Revolutionary WiFi-Based Human Pose Detection”, обещания отслеживания через стены, пульс/дыхание, людей и применение в безопасности; приложение даже сообщает “Connected to Rust sensing server”, хотя проверенная Compose-цель сейчас — Go. В `ui/README.md` также есть конкретные обещания по возможностям при 2–3 ESP32, не подтверждённые текущим Go backend.
- Текущая 3D-графика в отдельных компонентах строит условную комнату/пол и может создавать демонстрационные heatmap или фигуры. Это годится как визуальный прототип, но не является доказательством координат человека, этажа, высоты или распознавания классов объектов.

Перед удалением или переносом старого экрана необходимо проверить его реальные вызовы API, входящие ссылки, service-worker/cache поведение и полезные возможности. На этапе аудита отдельно сверить границы `ui/`, nvsim `dashboard/`, mobile app и desktop app; главный проектный runtime Go сейчас обслуживает именно `ui/`. Реализацию надо менять по сценариям, а не удалять большие файлы вслепую.

## 3. Принципы новой версии

1. **Сначала операторская задача.** Пользователь открывает приложение, чтобы понять состояние источника, наличие данных, состояние сенсоров и доступные измерения, а не читать маркетинговую страницу.
2. **Никаких выводов сильнее измерений.** Отличать `simulate`, RSSI-derived, ESP32 CSI live, stale/offline и калиброванные результаты. CSI-кадр сам по себе не является координатой человека. Hotspot поля — это поле сигнала, а не объект или track.
3. **Видимые происхождение и качество.** У каждого числа/слоя показывать источник, время последнего кадра/события, единицы и статус калибровки/модели. Уверенность не подавать как точность, если у неё нет проверенного смысла.
4. **Недоступная функция объяснима.** Неактивный сценарий сопровождается причиной: нет hardware, недостаточно свежих кадров, нет нужной калибровки, функция экспериментальная или endpoint ещё не реализован.
5. **Один понятный рабочий поток.** Подключить источник → увидеть свежие данные → проверить сенсоры → откалибровать комнату → записать/повторить → изучить поддерживаемую модель. Никаких опасных действий без подтверждения.
6. **UI остаётся статически раздаваемым Go-сервером.** Любое изменение сборки/фреймворка должно показать, как статические артефакты попадают в текущий Docker image, как работает offline shell и как тестируется выдача путей. Не вводить отдельный frontend-сервис в Compose без необходимости.

## 4. Предлагаемая информационная архитектура

### Общая оболочка

- **Боковая навигация** с небольшим числом пользовательских разделов, сгруппированных по задачам; на узком экране сворачивается в доступное drawer-меню.
- **Верхняя системная строка**: выбранный источник, состояние API и WebSocket, свежесть кадров, режим/происхождение данных и заметные предупреждения. Индикаторы имеют текст и иконку, а не только цвет.
- **Контекст текущего раздела**: заголовок, одно предложение о назначении, основные действия справа; второстепенные действия в меню.
- **Главная рабочая область** с независимой прокруткой там, где есть таблица/список/инспектор. Состояние фильтров и выбранной зоны сохраняется в URL, если ссылкой разумно поделиться.
- **Глобальная панель событий/ошибок** показывает краткое сообщение и доступный следующий шаг; не заменяет inline-ошибки рядом с проблемным полем или действием.

### Навигация и страницы

| Раздел | Задача пользователя | Содержимое и главное действие |
|---|---|---|
| **Обзор** | Понять, запущена ли система и есть ли реальные данные | Состояние backend/источника, свежесть последнего сигнала, узлы, активные возможности, заметная карточка режима `Demo / RSSI / CSI / нет кадров`; CTA зависит от состояния: запустить демо, подключить узел или перейти к настройке |
| **Пространство** | Исследовать сигнал и подтверждённые пространственные результаты | Единая сцена с явным выбором слоя: устройства/mesh, signal field, экспериментальная pose, валидированные tracks. Слой скрыт/disabled, если API не разрешает его; легенда сообщает, что именно отображается |
| **Датчики** | Проверить узлы и качество поступления CSI | Список узлов и инспектор выбранного узла: источник/ID, last seen, CSI rate, sequence/sync status, качество и причина stale/offline. Геометрия показывается только при заданной привязке |
| **Калибровка** | Привязать узлы к помещению и создать базовую модель | Последовательный поток: выбрать помещение/сетку → привязать узлы и геометрию → собрать валидные свежие кадры → ввести ground truth → сохранить и проверить trust/status. Сброс требует понятного подтверждения с описанием затрагиваемых данных |
| **Записи и данные** | Записать, изучить и воспроизвести доступные данные | Список записей, источник и synthetic watermark, фильтры по времени/узлу/меткам, детали и воспроизведение. Удаление/экспорт описывают, какие файлы затрагиваются |
| **Модели** | Понять активную модель и допустимые действия | Registry, тип/архитектура, схема весов, provenance, дата, состояние загрузки и доступный инференс. Обучение только для поддерживаемых activity-задач; `501` не превращать в будто бы действующую кнопку |
| **Интеграции** | Подключить поддерживаемый поток или приёмник | Каталог с capability, статусом и источником учётных данных; отдельно различать ingest-only, polling, настроено/не настроено и проверено на аккаунте/не проверено |
| **Настройки** | Настроить источник, безопасность и поведение интерфейса | URL/токен без показа секрета, тема, privacy, разрешённые сетевые параметры, состояния экспорта и доступности; пояснения по локальной/сетевой экспозиции |

**Сократить или перенести:** вкладки `Architecture`, `Performance` и `Applications` не должны конкурировать с live-панелью. Полезную справочную информацию переместить в отдельные страницы Help/Docs. `Pose Fusion` и `Observatory` до миграции пометить как labs/демо с видимой плашкой `Synthetic/Experimental`; сохранить рабочие ссылки и функции, пока аудит не подтвердит, что их можно заменить.

### Основные состояния экрана «Обзор»

1. **Первый запуск / нет узлов:** короткие шаги подключения и команда/инструкция для ESP32; явная кнопка демо с пометкой synthetic.
2. **Демо:** все графики и сценические данные маркируются как синтетические; невозможно спутать с CSI live.
3. **Узел подключён, кадры свежие, калибровки нет:** показывать входящие CSI и диагностику качества; метрическая локализация и vitals имеют статус недоступны.
4. **Источник RSSI:** разрешать только поля, реально основанные на RSSI, с заметной подписью `RSSI-derived`; не обозначать этот путь как CSI.
5. **Отключение, устаревшие данные, переподключение, ошибка auth:** указать последнее время получения, причину и действие восстановления. Не оставлять старые данные с зелёным статусом.

## 5. Отдельный крупный этап: общее многоуровневое 3D-пространство

Это самостоятельная инженерная инициатива, которая зависит от валидированной системы координат и данных backend. Её нельзя решить только заменой сетки пола на большой объёмный canvas.

### 5.1. Сначала определить физический смысл сцены

- Зафиксировать и версионировать систему координат: единицы, origin, направление осей, привязки sensor/node, преобразования между комнатой/этажом/зданием и погрешность.
- Определить иерархию `site → building → floor → room → zone`; этаж и высоту вводить только там, где они заданы калибровкой или измерены.
- Разделить модели `sensor`, `signal_field/hotspot`, `experimental_pose` и `validated_track`. Не подставлять сигналовую ячейку в тип координат track.
- Договориться о данных для неизвестного/потерянного track: age, confidence meaning, uncertainty/accuracy, calibration/model IDs, причина отсутствия. Если backend сейчас не предоставляет валидированный объектный трек, сцена показывает только сенсоры и signal field.

### 5.2. Вертикальный срез визуализации

1. Сначала собрать прототип сцены по синтетическому JSON fixture и реальному текущему payload. На каждом слое видны provenance и тип данных.
2. Сделать обзор пространства и переключение уровня/этажа/комнаты; добавить zoom/pan/orbit, fit-to-bounds, выбор узла и временной диапазон. Базовый 2D/плановый режим остаётся доступным без WebGL и с клавиатуры.
3. Добавить объёмное поле только если его ячейки, временная точка, координаты и единицы приходят из контракта, а не создаются UI-эвристикой. Маркеры человека включать лишь после валидированного backend track.
4. Для классов «человек/животное/птица/другие объекты» — отдельные детекторы, размеченные данные и критерии качества на held-out помещениях. Визуальная иконка или DEMO-объект не считается детекцией.
5. Проверить пустую, перегруженную, многоэтажную, частично устаревшую сцену и WebGL недоступный/потерянный контекст; добавить ограничение частоты кадров и очистку render loop ресурсов.

**Критерий go/no-go для live-объектов:** API имеет метрические координаты, калибровку, track ID, время, смысл confidence и uncertainty; точность/ошибки измерены на независимом ground truth и подтверждены на реальном оборудовании. До этого 3D-сцена остаётся visualizer-ом сигнала/сенсорной топологии, не «радаром людей».

## 6. Дизайн-система

Исходный визуальный референс пользователя: `DESIGN-linear.md` (передан в `Downloads`) и перекрёстный референс `awesome-design-md/design-md/linear.app/DESIGN.md`. Существующий проектный ADR: `docs/adr/ADR-053-ui-design-system.md`. Применить их к RuView как к инструменту мониторинга, не копировать название, логотип, текст или маркетинговую композицию Linear.

- **Атмосфера:** спокойная тёмная инструментальная панель: ровные поверхности, чёткая типографическая иерархия, аккуратные рамки; визуальный сигнал важнее декоративных эффектов. Тёмная тема остаётся основной. Текущий переключатель темы проверить и либо довести до целостной светлой темы, либо убрать незавершённый режим из рабочего UI до отдельного решения.
- **Цветовые роли:** глубокий фон, ступени поверхности, основной/вторичный/служебный текст; индиго `#5e6ad2` только для действия/фокуса/ссылки; success/warning/error — семантически. Для сенсорных heatmap выбрать отдельную шкалу и легенду, не переиспользовать цвет статусов.
- **Контраст:** значения из референса — исходная точка, но не автоматическая гарантия. Например, в самом файле для белого текста на `#5e6ad2` указано 3.6:1, что нельзя без проверки трактовать как годное для любой кнопки и кегля. Для обычного текста целиться в WCAG 2.2 AA (4.5:1), для крупных — в установленный порог; компоненты/фокус проверять отдельно. [WCAG 2.2 — спецификация W3C](https://www.w3.org/TR/WCAG22/)
- **Типографика:** нейтральный sans для интерфейса; Inter Variable использовать при наличии локального файла и соблюдении лицензии, иначе system stack. Berkeley Mono только при разрешённом локальном распространении; иначе системный monospace. Временные метки, IDs и сырые числа выравнивать табличными цифрами, если выбранный шрифт их поддерживает.
- **Ритм/сетка:** базовый шаг 4 px; токены для основных интервалов, высоты control, радиусов и размеров иконок; единые container/grid и правила для заголовка/toolbar/table. Избегать отдельных вручную подобранных margin в каждом HTML.
- **SVG-иконки:** единый согласованный набор outline-иконок, один viewBox/оптический размер/stroke; понятные состояния active/disabled/focus. Не использовать emoji, случайные Unicode-пиктограммы или разные наборы начертаний для управляющих функций.
- **Компонентные состояния:** default, hover, pressed, focus-visible, disabled с причиной, loading, empty, error, offline, stale. Таблицы, статусы, forms, dialogs, toasts, tooltips и destructive confirmation должны быть описаны до переиспользования.
- **Движение:** короткие 100–200 ms переходы для состояния и навигации; никаких постоянных пульсирующих панелей или пружинистых эффектов в инструменте. Уважать `prefers-reduced-motion`; realtime animation в сцене — только для реально поступивших данных и с возможностью pause.
- **Адаптивность:** предусмотреть desktop с постоянным sidebar, узкое окно со свёрнутым sidebar и мобильный drawer/нижние действия. Для сцены отдельно определить touch controls, viewport, вертикальную ориентацию и доступную текстовую/табличную альтернативу.

## 7. Технический подход и границы архитектуры

### 7.1. Решение по UI-стеку

Исходный код — vanilla HTML/CSS/ES modules с существующими сервисами и `node --test`. **Предварительная рекомендация — не переписывать frontend в React/Vue автоматически:** сначала очистить границы, проверить router/state и провести один вертикальный spike для новой оболочки + live overview. В spike сравнить поддержку маршрутов/истории, UI-state, типизированных API-контрактов, тестируемости, WebGL сцены, сборки контейнера и offline static serving.

Если текущий подход после spike требует большого ручного DOM/state-кода, оформить решение о Vue 3 + TypeScript + Vite (либо одном выбранном аналоге) отдельным ADR и переходить по одному маршруту. Нельзя смешивать два фреймворка, переписывать все страницы одним шагом или добавлять зависимость только ради стилизации. При любом варианте Go Compose остаётся единственной runtime-точкой; если нужен frontend build, он выполняется в build-stage Docker и отдаёт статические файлы Go.

### 7.2. Модули и data boundary

- Разделить приложение на `app shell`, маршруты/страницы, доменные features (overview, devices, calibration, recordings, models, integrations, space), общий design system и слой API/stream.
- Один API client: base URL, auth, timeout/cancellation, JSON/error envelope, request IDs и единая обработка unauthorized/offline. Не читать local storage и строить fetch независимо в каждом компоненте.
- Описать только реальные UI-потребляемые схемы Go endpoints и WebSocket envelopes; добавить контрактные проверки fixture ↔ backend. Расширять схему при согласовании API, не придумывать поля для визуализации.
- WebSocket manager централизует билет auth, connect/disconnect, backoff, heartbeat, stale transition, duplicate suppression и disposal при уходе со страницы. Обновления большого 3D canvas агрегировать/ограничивать по render cadence, UI должен показывать последнюю реальную timestamp.
- Mock/simulator включать явным переключателем «Демо»; fixture содержат synthetic provenance. В случае недоступного backend по умолчанию показывать error/offline, не незаметно подменять источник.
- CSS разделить на токены, reset/base, layout, shared components, feature styles и темы. Перед удалением legacy utility-подобных компонентов составить карту import/use и покрыть заменяемые сценарии тестом.

## 9. Критерии готовности frontend

- Новому пользователю ясно, какой источник подключён и live ли данные; synthetic, RSSI, ESP32 CSI, stale/offline не смешиваются.
- Основная навигация обслуживает операторские задачи, а Help/Docs не конкурирует с мониторингом.
- Каждая цифра/карта/анимация имеет контракт источника, единицы, timestamp и состояние; нет чисел-плейсхолдеров, похожих на measured.
- Все поддерживаемые backend действия работают end-to-end; все неподдерживаемые явно объяснены и не запускаются как будто успешные.
- Важные переходы сохраняют URL/back-forward, WebSocket корректно reconnect/dispose и состояния ошибки восстанавливаемы.
- Компоненты консистентны по сетке, типографике, spacing, SVG, keyboard, hover/focus/disabled/error/loading/empty; small text contrast проверен измерением, а не по таблице цвета из референса.
- Browser evidence есть на desktop, tablet и mobile; в smoke-test нет uncaught errors, битых запросов/страниц, разрыва между API контрактом и UI.
- 3D не показывает человека, животное, птицу, этаж или точную координату, которых нет в валидированных данных. Перспективный универсальный объектный детектор имеет отдельный dataset/model/ground-truth gate.

## 10. Риски и решения

| Риск | Мера |
|---|---|
| Повторить красивую сцену, скрывающую, что данных нет | Сначала provenance contract и offline/synthetic сценарии; пустое состояние — полноценное состояние продукта |
| Переписать framework и UI одновременно | Сначала вертикальный spike и отдельное ADR; менять по одному слою/route |
| Потерять функциональность старых панелей | Инвентаризация routes, imports, API calls, service worker и ссылки перед удалением |
| Ложные тревоги/измерения (пульс, дыхание, count, position) | Удалить неподтверждённые static claims; показывать только capability server и метку доказанности |
| 3D тяжёлая или недоступна на слабом GPU | Lazy loading, ограничение кадров и объектов, управление ресурсами, 2D/text fallback |
| Цветовая тема не отвечает контрасту | Пересчитать foreground/background, focus и графики; проверить WCAG 2.2 AA, не копировать таблицу без измерения |
| Секрет в browser storage или диагностике | Сверить текущую OAuth/API-token модель, не логировать secret, masked display и безопасный logout/cache purge |

## 11. Как будет вестись дальнейшая работа

Работать сверху вниз по этапам 0–6, начиная с одного законченного пользовательского сценария и проверяя его с реальным Go API после каждого вертикального среза. Этап 7 (общая multi-floor 3D сцена и объектные треки) оценивать отдельно по готовности данных и hardware, чтобы UI-работа не подменяла sensing-разработку. На каждом изменённом экране фиксировать состояние до/после, тестировать браузером и исправлять обнаруженные проблемы до перехода к следующему этапу. До реального ESP32 capture и независимой оценки результата обозначать любые измерительные выводы как synthetic, experimental или unavailable.

## 12. Итог доработки интерфейса — 2026-10-10

Последняя реализация заменяет первоначальную навигацию и решение о сохранении Labs.
Визуальный контракт находится в `ui/workspace/DESIGN.md` и следует предоставленному
`DESIGN-linear.md`. Светлая и тёмная темы реализованы общими токенами; кнопка
солнца/луны в хедере сохраняет выбор и синхронизирует вкладки. До выбора используется
тема ОС. При смене темы цвета применяются сразу, без промежуточного низкого контраста.

### Реализовано

- Основная навигация: Monitor, Devices, Calibration, Recordings, Models, Settings.
  Help остаётся вторичным; Integrations доступен через Settings с обратной ссылкой.
- Monitor: понятные показания сигнала и последовательность устройства → калибровка →
  запись. Убраны декоративные метрики, повторяющиеся панели и крупная сетка по умолчанию.
- Space объединён с Monitor; диагностическая сетка раскрывается отдельно. Старый
  bookmark перенаправляется. Observatory/Pose Fusion больше не запускают симуляторы,
  камеры, сценарных людей или панели псевдобиометрии; старые URL открывают Monitor.
- Mesh, CSI/trust, настройка счётчика, параметры обучения и расширенные настройки
  раскрываются по запросу. Поддерживаемые API-действия сохранены.
- Локальный Inter Variable, единый Lucide sprite, размеры/радиусы/отступы и цвета
  приведены к контракту. Контраст семантического текста адаптирован к обеим темам.
- Исправлены undefined identity в действиях калибровки, зависание загрузки статических
  страниц и изменение маршрута по Skip to content. Обновление сохраняет раскрытые
  секции. Синтетический источник не позволяет начать калибровку комнаты.
- Проверка API access обращается к API info. Ошибка авторизации имеет приоритет над
  старым синтетическим состоянием. HTML обновляется по сети; API-ответы не кэшируются.
